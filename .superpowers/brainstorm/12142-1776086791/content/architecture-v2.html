重构架构方案 — 以 Agent 生态为核心

目标：让简历和面试都围绕 LangChain / LangGraph / RAG / Agent 展开

A

方案 A：LangGraph 驱动引擎（推荐）

核心思路：前端 React Flow 负责可视化编排，后端将画布 JSON 编译为 LangGraph StateGraph 执行

前端 React Flow → 画布 JSON → FastAPI → 编译为 → LangGraph StateGraph
  ├── LLM Node → LangChain ChatModel (多 Provider)
  ├── RAG Node → LangChain Retriever + VectorStore
  ├── Agent Node → ReAct Agent (自主 Tool Calling)
  ├── TTS Node → LangChain Tool (音频合成)
  └── SSE → 实时推送节点状态到前端

优势

  • LangGraph 原生支持状态图、条件分支、循环
  • 面试亮点最多：LangGraph + LangChain + RAG + Agent 全覆盖
  • LangSmith 可接入做调试追踪（又一个加分项）
  • 前端画布 → LangGraph 的编译过程本身就是很好的技术话题

注意

  • LangGraph 学习曲线稍陡
  • 需要设计好画布 JSON → StateGraph 的映射逻辑
B

方案 B：LangChain LCEL 链式引擎

核心思路：不用 LangGraph，用 LangChain 的 LCEL (LangChain Expression Language) 将节点串成 Chain 执行

前端 React Flow → 画布 JSON → FastAPI → 编译为 → LCEL RunnableSequence
  ├── ChatPromptTemplate | ChatModel | OutputParser
  ├── Retriever | LLM (RAG 链)
  └── Custom Runnable (TTS)

优势

  • LCEL 更简单直接，学习成本低
  • 适合线性链式流程

局限

  • 不支持条件分支和循环，图表达能力弱
  • 面试深度不如 LangGraph
  • Agent 自主决策能力有限

💡 推荐方案 A

LangGraph 就是为"图执行"设计的，和我们的"流图执行面板"天然匹配。而且它带来的面试话题密度最高：

  • 图编译："我如何将前端可视化画布编译为 LangGraph 状态图"
  • 状态管理："LangGraph 的 State 如何在节点间传递和累积"
  • Agent 推理："ReAct Agent 节点如何自主决定调用哪个工具"
  • RAG 流程："检索增强生成的完整链路：Embedding → 向量检索 → Reranking → LLM"
  • 可观测性："通过 LangSmith 追踪每次执行的 Token 用量和延迟"
