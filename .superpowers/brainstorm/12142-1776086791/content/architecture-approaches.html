架构方案对比

基于需求：React + React Flow 前端 / FastAPI 后端 / SQLite / 多 LLM 原生接口 / TTS 抽象层

A

方案 A：同步执行 + SSE 推送（推荐）

架构：前端 React SPA ← SSE → FastAPI 后端 ← 同步引擎

工作流引擎：后端内置轻量 DAG 引擎，按拓扑序依次执行节点。每个节点执行完毕通过 SSE 推送状态到前端。

优势

  • 实现最简单，V1 完全够用
  • SSE 天然支持实时节点状态推送
  • 无需消息队列等额外基础设施
  • 调试体验好，节点逐个点亮

局限

  • 不支持并行分支执行
  • 长时间任务占用服务器线程
B

方案 B：异步任务队列 + WebSocket

架构：前端 React SPA ← WebSocket → FastAPI → Celery/RQ 任务队列 → Worker

工作流引擎：工作流提交到任务队列，Worker 异步执行，通过 WebSocket 双向通信推送状态。

优势

  • 支持并行分支、长时间任务
  • 可水平扩展 Worker
  • WebSocket 双向通信更灵活

局限

  • 需要 Redis/RabbitMQ 等额外服务
  • 复杂度高，V1 阶段过度设计
  • 调试和错误处理更复杂
C

方案 C：混合方案 — SSE 起步，预留异步扩展

架构：前端 React SPA ← SSE → FastAPI → 内置引擎（接口抽象，后续可替换为队列）

工作流引擎：定义清晰的 ExecutionEngine 接口。V1 用同步+SSE 实现，未来可替换为异步队列实现，前端无需改动。

优势

  • V1 简单快速，和方案 A 一样轻
  • 接口抽象使未来迁移平滑
  • 前端只依赖 SSE 事件格式，不关心后端实现

局限

  • 抽象层需要提前设计好，有一定前期成本
  • V1 本身仍然是同步执行

💡 我的推荐：方案 A

对于功能完整的 V1 来说，方案 A 的同步 DAG 引擎 + SSE 是最务实的选择。它足以支撑"用户输入 → LLM → TTS → 音频播放"的链路，实时节点状态推送体验好，且没有额外基础设施依赖。方案 C 的抽象层在当前阶段是 YAGNI（你不会需要它），等真正需要异步执行时再重构也不迟。
